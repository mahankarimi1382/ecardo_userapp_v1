# معیار خروج مرحلهٔ ۳

## Gate A — Coverage
- [ ] هر صفحه/route کشف‌شده یک شناسهٔ پایدار دارد.
- [ ] برای هر route مشخص است که UI، رفتار، accessibility، localization و QA چه وضعیتی دارند.
- [ ] routeهای runtime-verified از کاندیداهای static scan تفکیک شده‌اند.
- [ ] صفحه‌های محافظت‌شده یا غیرقابل‌دسترسی به‌صورت blocker ثبت شده‌اند، نه حذف‌شده.

## Gate B — Visual & UX
- [ ] همهٔ صفحه‌ها از design token و componentهای تأییدشده استفاده می‌کنند یا دلیل انحراف دارند.
- [ ] وضعیت‌های loading/empty/error/offline/disabled مطابق کاربرد صفحه پیاده شده‌اند.
- [ ] فرم‌ها، اعتبارسنجی، پیام خطا، تأیید و بازگشت کاربر قابل‌فهم‌اند.
- [ ] چیدمان در عرض‌های هدف و زبان‌های RTL/LTR بررسی شده است.
- [ ] حرکات ترجیحی سیستم و Reduce Motion رعایت شده است.

## Gate C — Functional integrity
- [ ] UI با قراردادهای مرحلهٔ ۲ سازگار است.
- [ ] صفحه/دکمهٔ مالی صرفاً به‌خاطر ظاهر خوب «موفق» نشان نمی‌دهد.
- [ ] مبلغ، ارز، کارمزد، وضعیت تراکنش و منبع حقیقت از دادهٔ معتبر می‌آیند.
- [ ] دکمه‌های دوبارکلیک، timeout، pending، retry و نتیجهٔ نامعلوم سناریو دارند.
- [ ] اطلاعات حساس در log، screenshot و analytics افشا نمی‌شود.

## Gate D — Evidence & Regression
- [ ] screenshot قبل/بعد یا توضیح مستند عدم امکان ثبت شده است.
- [ ] تست هر مسیر و حالت مهم با نتیجهٔ واقعی ثبت شده است.
- [ ] تحلیل ایستا و تست‌ها در محیط مجاز پاس شده یا خطای باقی‌مانده دقیق گزارش شده است.
- [ ] هیچ P0/P1 باز بدون پذیرش ریسک و owner باقی نمانده است.
- [ ] کاتالوگ و گزارش handoff برای هر مورد بررسی‌نشده، دلیل و اقدام بعدی دارند.

هر checkbox باید براساس شواهد واقعی تکمیل شود، نه براساس ادعای ایجنت.
