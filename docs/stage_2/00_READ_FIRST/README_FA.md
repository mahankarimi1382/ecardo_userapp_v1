# eCardo — مرحلهٔ ۲: یکپارچه‌سازی، رفع ریسک‌های بحرانی و آماده‌سازی ارتقای سراسری

**تاریخ تهیه: ۲۳ اکتبر ۲۰۲۶**

## هدف
این مرحله بین «کشف و نقشه‌برداری» و «ارتقای همهٔ صفحات» قرار می‌گیرد. خروجی آن باید قراردادهای روشن بین ماژول‌ها، اولویت‌بندی واقع‌بینانهٔ شکاف‌ها و اصلاحات کوچک اما اثبات‌شده باشد؛ نه تغییر گسترده و بدون traceability.

## شرط شروع
ایجنت باید در checkout واقعی مخزن `mahankarimi1382/ecardo_userapp_v1` اجرا شود. ابتدا خروجی مرحلهٔ ۱ را پیدا کند: `docs/app-map/`، `DISCOVERY_SUMMARY.md`، کاتالوگ Routeها، ماتریس صفحه/سرویس، کاتالوگ فلوها و GAP Register.

اگر خروجی‌های مرحلهٔ ۱ موجود نیستند، ناقص‌اند یا به SHA دیگری تعلق دارند، **ابتدا اجرای مرحلهٔ ۱ را تکمیل یا دوباره اجرا کن**. به‌هیچ‌وجه دادهٔ نمونه یا حدس را به‌عنوان inventory واقعی جا نزن. پس از این تطبیق، مرحلهٔ ۲ می‌تواند در دامنه‌های دارای شواهد جلو برود و موارد فاقد شواهد را BLOCKED علامت بزند.

## قانون عدم جعل نتیجه
این بسته یک دستورکار اجرایی است، نه گزارش ممیزی اجراشده روی checkout فعلی. هیچ موردی در کاتالوگ‌ها تأییدشده محسوب نمی‌شود تا عامل اجرایی، مسیر واقعی فایل، SHA، تست یا شاهد قابل‌بررسی را ثبت کند.

## تعریف موفقیت
- هر قرارداد فقط بعد از تطبیق با کد و backend واقعی به `CONFIRMED` می‌رسد.
- ریسک‌های P0/P1 با اثر، شواهد، اصلاح، تست و نتیجهٔ re-test ثبت می‌شوند.
- تغییرات هر ماژول به Route/Flow ID و تسک مشخص متصل است.
- تست‌ها به‌وسیلهٔ integrator و طبق دستور پروژه اجرا می‌شوند؛ تست‌های Flutter به‌صورت موازی روی shared worktree اجرا نمی‌شوند.
- هیچ push، tag، release، deploy یا عملیات مالی واقعی انجام نمی‌شود.

## بسته‌های قبلی
این مرحله مکمل بستهٔ کشف مرحلهٔ ۱ و بستهٔ جامع UI/UX و یکپارچگی است. بنچمارک XPay/xMoney/xPortal فقط برای الگوهای محصول و UX است؛ مرجع قواعد مالی eCardo، قرارداد واقعی backend و تست‌ها هستند.
