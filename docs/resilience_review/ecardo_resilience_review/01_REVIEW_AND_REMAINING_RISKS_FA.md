# eCardo — بازبینی مقاوم‌سازی Exchange، Passcode و صدور کارت

**تاریخ:** ۱۷ اکتبر ۲۰۲۶  
**دامنه:** شش جریان مالی، دریافت تنظیمات، retry، Idempotency، سفارش کارت، ارائه‌دهنده، CI و شواهد تست  
**وضعیت شواهد:** این بررسی بر گزارش فنی کاربر و نسخه عمومی مخزن Flutter تکیه دارد. checkout محلی، مخزن بک‌اند خصوصی، دیتابیس سرور، log زنده و emulator این جلسه در دسترس مستقیم نیستند؛ بنابراین تغییرات محلی/سرور به‌طور مستقل تأیید نشده‌اند.

## 1. حکم اجرایی

گزارش تازه جهت‌گیری مناسبی دارد: خطاهای تنظیمات و پس‌کد را به شش ماژول توسعه داده، پیش‌اعتبارسنجی موجودی افزوده و ارائه‌دهنده آزمایشی را از مسیر کاربر خارج کرده است. با این حال، عبارات «۱۰۰٪ رفع قطعی» و «پیشگیری همیشگی» بدون مشاهدهٔ کد، قرارداد بک‌اند و شواهد تست staging قابل تأیید نیستند.

تا قبل از انتشار باید موارد P0 و P1 این سند به‌صورت قابل بازتولید بسته شوند. هیچ چیزی در این سند به معنی مجوز push، انتشار، تغییر سرور یا تغییر دیتابیس نیست.

## 2. وضعیت شواهد و محدودیت تأیید

- گزارش ارائه‌شده اعلام می‌کند `flutter analyze` موفق، `flutter test` دارای ۷۲۲ تست موفق و `verify_release_metadata.py` سبز است؛ خروجی خام اجرای همان checkout در این جلسه موجود نیست.
- صفحه عمومی README مخزن در زمان بررسی همچنان ۶۴۶ تست را توصیف می‌کند و تغییرات محلی گزارش‌شده در بخش‌های Exchange/Card در آن قابل اثبات نیستند: https://github.com/mahankarimi1382/ecardo_userapp_v1
- مخزن بک‌اند `ecardo-backend` و مسیرهای PHP معرفی‌شده در گزارش از طریق URL عمومی بررسی‌شده قابل دریافت نبودند؛ پس تغییر `PUBLIC_SETTINGS`، غیرفعال‌سازی افزونه در دیتابیس و نتیجه `curl` را باید با شواهد محافظت‌شدهٔ deploy و تست تأیید کرد.
- «working tree clean» با «تغییرات push نشده‌اند» سازگار است، اما باید با `git status -sb`, `git log origin/main..HEAD`, `git tag --list` و `git diff origin/main...HEAD` ثابت شود.

## 3. P0 — fallback پس‌کد باید محدود، نوع‌دار و بدون loop باشد

### ریسک
گزارش می‌گوید هر پاسخ `422` که متن آن شامل `passcode` است، popup را باز کرده و درخواست را با رمز واردشده به‌طور خودکار retry می‌کند. اگر پیام خطای «رمز نامعتبر» نیز همین مسیر را فعال کند، امکان حلقهٔ popup/retry، UX گیج‌کننده، درخواست‌های زیاد و رفتارهای تکراری وجود دارد. متن خطا هم می‌تواند در زبان‌های مختلف، با تغییر بک‌اند یا قالب پاسخ تغییر کند.

### الزام پیاده‌سازی

1. از کد خطای ساختاریافته استفاده شود، نه substring روی متن کاربرپسند. قرارداد پیشنهادی:
   - `PASSCODE_REQUIRED`: عملیات قبلاً اجرا نشده؛ گرفتن رمز و ادامه مجاز است.
   - `PASSCODE_INVALID`: رمز نامعتبر است؛ پیام inline و تعداد تلاش محدود، بدون auto-retry نامحدود.
   - `PASSCODE_NOT_CONFIGURED`: کاربر باید ابتدا رمز بسازد؛ popup ورود رمز کافی نیست.
   - `PASSCODE_LOCKED`: توقف عملیات و نمایش زمان/روش بازیابی طبق سیاست سرور.
   - `SETTINGS_UNAVAILABLE`: وضعیت نامعلوم؛ تنظیمات دوباره دریافت یا عملیات حساس fail-closed شود.
2. برای هر submission، حداکثر یک recovery prompt خودکار مجاز باشد. پس از retry ناموفق، کنترل به کاربر واگذار شود و حلقهٔ خودکار ایجاد نشود.
3. دکمهٔ لغو/بستن popup باید بدون ارسال درخواست جدید، صفحه و draft تراکنش را به وضعیت امن بازگرداند.
4. رمز عبور/پس‌کد نباید در log، analytics، crash report، SharedPreferences، DLQ یا متن exception ثبت شود.
5. درخواست اصلی و retry باید از یک state machine صریح عبور کنند؛ flagهای پراکنده در شش controller منبع رفتار مستقل و drift نشوند.

## 4. P0 — قرارداد retry و Idempotency برای تغییر payload

### ریسک
در درخواست اول ممکن است `passcode` وجود نداشته باشد و در retry اضافه شود. اگر fingerprint سرور تمام بدنه را شامل شود، همان idempotency key با body متفاوت ممکن است conflict بدهد. برعکس، ساختن کلید تازه پس از خطای مبهم ممکن است یک عملیات مالی را دوباره ثبت کند.

### قرارداد پیشنهادی

- یک `operation_id` یکتا برای **قصد مالی** هنگام آغاز جریان تولید شود و در طول retryها پایدار بماند.
- بک‌اند ابتدا مجوز/پس‌کد را بررسی کند و تضمین کند خطای `PASSCODE_REQUIRED` قبل از هر اثر مالی و قبل از commit ایجاد می‌شود.
- کلید idempotency به رکورد سمت سرور با scope کاربر + endpoint + operation id متصل شود؛ ذخیره نتیجه، وضعیت `in_progress/succeeded/failed_final/unknown` و اعمال ledger باید در transaction/قفل مناسب انجام شوند.
- اسرار احراز (passcode/OTP/token) نباید به‌صورت خام ذخیره یا log شوند. fingerprint عملیات باید براساس intent کسب‌وکاری نرمال‌شده تعریف شود و قرارداد تغییر فیلد تأیید امنیتی در آن مستند باشد.
- اگر سرور کلید را قبلاً با درخواست در حال اجرا دیده باشد، نتیجهٔ قبلی یا وضعیت عملیات را برگرداند؛ عملیات مالی تازه نسازد.
- پاسخ 4xx تنها زمانی terminal و قابل آزادسازی است که کد خطا صریحاً به معنی عدم انجام عملیات باشد. 5xx، timeout، قطع سوکت و قطع برنامه نتیجه را مبهم می‌گذارند تا استعلام سمت سرور انجام شود.
- `Idempotency-Key` و `X-Idempotency-Key` نباید کورکورانه هر دو ارسال شوند؛ باید یک header canonical در قرارداد API انتخاب شود. اگر سازگاری با سرورهای قدیمی لازم است، رفتار آن‌ها مستند و conflict بین دو مقدار رد شود.

## 5. P0 — هیچ تصمیم مالی صرفاً در کلاینت قطعی نیست

### موجودی کارت
مقایسهٔ موجودی با `هزینه صدور + مبلغ شارژ اولیه` فقط برای بهبود تجربه کاربری مناسب است. داده ممکن است کهنه باشد یا دو درخواست موازی موجودی یکسانی ببینند.

بک‌اند باید هنگام سفارش:
1. قیمت و کارمزد و ارز را از منبع معتبر محاسبه کند؛
2. نرخ/quote را با شناسه، نسخه و expiry مشخص تثبیت کند؛
3. موجودی را در transaction اتمیک بررسی و reserve/debit کند؛
4. سفارش و اثر ledger را idempotent ثبت کند؛
5. در شکست issuer، refund/void یا saga compensation قابل تکرار داشته باشد؛
6. پاسخ نهایی سفارش را از روی وضعیت معتبر سرور برگرداند.

### ارائه‌دهنده و کشور
فیلتر UI به‌تنهایی مانع درخواست مستقیم API یا نسخهٔ قدیمی اپ نمی‌شود. eligibility باید در سرور با country/residency، نوع حساب، ارز، محصول، وضعیت قراردادی issuer و سیاست انطباق کنترل شود. از تلاش برای دورزدن محدودیت‌های ارائه‌دهنده پرهیز شود.

### وضعیت صادرکننده داخلی
نام `LicensedIssuerPlaceholder` از نظر معنایی احتمال placeholder بودن integration را مطرح می‌کند. قبل از نمایش آن به‌عنوان کارت واقعی/دارای مجوز، باید قرارداد issuer، محیط production، BIN/program ownership، فرایند صدور/لغو، reconciliation و افشای شرایط محصول مستند باشند. اسم کلاس به‌تنهایی اثبات مجوز یا اتصال واقعی نیست.

## 6. P1 — همگام‌سازی تنظیمات پس‌کد

- برای config state سه حالت تعریف شود: `enabled`, `disabled`, `unknown`; نبود کلید یا timeout هرگز به‌طور ضمنی `disabled` تلقی نشود.
- مقادیر `"1"`, `"0"`, `true`, `false`, null و کلید ناشناخته طبق schema مستند parse شوند؛ مقدار غیرمنتظره به حالت `unknown` برود.
- وضعیت عمومیِ پس‌کد فقط باید flag فعال/غیرفعال باشد؛ هیچ hash، salt، policy secret، credential یا دادهٔ حساب کاربر به endpoint عمومی اضافه نشود.
- تغییرات تنظیمات باید cache invalidation/versioning داشته باشند تا Octane، کش برنامه و کلاینت وضعیت قدیمی را برای مدت نامعلوم نگه ندارند.
- endpoint باید قرارداد واضح و نسخه‌پذیر داشته باشد؛ test contract برای تمام شش تنظیم و برای حالت حذف/خطای پاسخ اضافه شود.
- اگر setting نامشخص است و `hasPasscode` محلی stale یا ناموجود است، عملیات به صورت fail-closed کنترل شود: settings دوباره دریافت شود یا بک‌اند challenge تایپ‌دار ارائه کند؛ به وضعیت خاموش فرضی ادامه داده نشود.

## 7. P1 — پشتیبانی aliasهای funding source

پذیرفتن `wallet` و `irr_wallet` می‌تواند مهاجرت سازگار باشد، اما باید:
- ورودی در ابتدای مرز API به یک enum canonical تبدیل شود؛
- اگر دو فیلد ناسازگار همزمان آمدند درخواست رد شود؛
- alias فقط در endpoint/نسخه‌های موردنظر پذیرفته شود؛
- تست قرارداد کلاینت قدیمی و جدید وجود داشته باشد؛
- شمارش استفاده از alias قدیمی بدون ثبت PII انجام شود و پس از مهاجرت، حذف alias قدیمی برنامه‌ریزی شود.

## 8. ماتریس حداقلی رگرسیون شش عملیات مالی

برای هر کدام از Exchange، Transfer، Cash Out، Withdraw، Make Payment و Create Gift، همهٔ حالت‌های زیر تست شوند:

1. setting=`enabled`, `disabled`, `unknown`, کلید غایب، timeout، پاسخ malformed؛
2. کاربر passcode دارد/ندارد، وضعیت پروفایل stale است؛
3. رمز درست، رمز نادرست، لغو popup، popup بسته‌شده با back، قفل حساب؛
4. `PASSCODE_REQUIRED` و سپس رمز صحیح: دقیقاً یک اثر مالی؛
5. `PASSCODE_INVALID`: تعداد prompt محدود، بدون loop؛
6. timeout/5xx پس از دریافت درخواست: استعلام وضعیت، نه عملیات جدید؛
7. دو tap سریع، دو request همزمان، process death و restart؛
8. localeهای فارسی/عربی/انگلیسی و نمایش خطا بدون وابستگی به متن ترجمه‌شده؛
9. اطمینان از عدم ثبت passcode/token/payload حساس در log و crash analytics.

## 9. ماتریس صدور کارت و provider

- کیف پول کافی/ناکافی و تغییر موجودی بین validation کلاینت و سرور؛
- دو درخواست موازی برای آخرین موجودی؛
- هزینه و شارژ اولیه با ارزهای مختلف، quote منقضی و rounding؛
- provider مجاز/غیرمجاز، کشور پشتیبانی‌نشده، provider خاموش، credential نامعتبر، timeout، 403، 422 و 5xx؛
- provider فهرست‌شده در کلاینت ولی disabled در سرور؛ endpoint باید سمت سرور رد کند؛
- aliasهای `wallet` و `irr_wallet` و مقادیر متناقض؛
- موفقیت issuer ولی timeout سمت کلاینت و retry بعدی؛ باید همان سفارش قبلی بازیابی شود؛
- شکست issuer بعد از reserve/debit؛ compensation/refund باید دقیقاً یک‌بار انجام شود؛
- بررسی سازگاری نام کارت، صادرکننده واقعی، شرایط محصول و مجوزهای ادعاشده.

## 10. Observability و حالت‌های پیش‌بینی‌نشده

- برای هر operation یک correlation id غیرحساس ثبت شود؛ operation id از passcode یا اطلاعات شخصی مشتق نشود.
- eventهای ساختاریافته تعریف شوند: `transaction.intent_created`, `passcode.challenge_required`, `passcode.validation_failed`, `transaction.unknown_result`, `transaction.reconciled`, `card.order_rejected`, `provider_unavailable`.
- log نباید token، passcode، PAN، CVV، IBAN کامل، payload خام یا اطلاعات KYC را ذخیره کند؛ از allowlist فیلدهای log استفاده شود نه فقط blacklist کلیدها.
- alert روی رشد `unknown_result`, passcode 422, provider 403/5xx, DLQ و mismatch ledger/settlement تنظیم شود.
- runbook برای «نتیجه مبهم»، «issuer ناموجود»، «config stale»، «Octane cache stale»، «دو بار tap»، «اپ بعد از ارسال بسته شد» و «refund ناموفق» نوشته شود.
- retry policy باید exponential backoff + jitter و سقف تلاش داشته باشد؛ عملیات مالی خودکار بدون operation id پایدار retry نشود.

## 11. معیارهای پذیرش نهایی

تسک صرفاً وقتی `PASS` می‌شود که همه موارد مرتبط تکمیل باشند:

- [ ] شش عملیات مالی با همان state machine و کد خطای تایپ‌شده کار می‌کنند.
- [ ] هیچ loop خودکار برای 422 وجود ندارد.
- [ ] یک intent در timeout/5xx/restart حداکثر یک اثر مالی دارد.
- [ ] دو intent مستقل با بدنه برابر مستقل می‌مانند.
- [ ] retry با passcode تکمیل‌شده با قرارداد idempotency سازگار است.
- [ ] موجودی و eligibility در بک‌اند اتمیک کنترل می‌شوند.
- [ ] provider خاموش/غیرمجاز در UI و API رد می‌شود.
- [ ] هیچ secret/PII حساس به log یا صف آفلاین راه نمی‌یابد.
- [ ] آمار تست با log raw همان commit تطبیق دارد.
- [ ] APK Release واقعی روی emulator نصب و تست شده است.
- [ ] backend staging و logها شواهد قابل بازتولید دارند.
- [ ] نسخه، SHA، tag، artifact، CI و سند release کاملاً هماهنگ‌اند.
- [ ] هیچ push/Release/deploy بدون تأیید صریح مالک انجام نمی‌شود.

## 12. وضعیت لازم در گزارش بعدی

برای هر تسک یکی از وضعیت‌ها ثبت شود:
- `CONFIRMED`: کد در SHA مشخص بررسی شده؛
- `REPRODUCED`: با تست/شبیه‌ساز قابل تکرار شده؛
- `VERIFIED_STAGING`: قرارداد بک‌اند و اثر مالی در staging تأیید شده؛
- `BLOCKED`: دسترسی سرور، حساب آزمایشی یا credential لازم است؛
- `NOT_DONE`: هنوز پیاده‌سازی نشده است.

عبارات «۱۰۰٪ رفع قطعی» و «پیشگیری همیشگی» تا وقتی شواهد مربوط به کد، backend و تست در کنار هم نیستند استفاده نشوند.
